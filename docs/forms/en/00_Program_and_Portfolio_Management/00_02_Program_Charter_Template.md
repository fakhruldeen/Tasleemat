<!--  
LLM INSTRUCTIONS: Fill in the [ Add details... ] placeholders based on project context.

The program charter is the document that authorises a program. It states why the
program exists, what it is accountable for delivering, and what authority and
resources have been given to the program manager in order to deliver it. It is
the point at which a group of individually sensible projects becomes a program
with a single accountable owner and a single set of objectives.

The intent behind separating the components from the objectives is that the two
are routinely confused: components describe what exists, objectives describe what
must change. A program whose component list could be pasted into the objectives
section has not yet decided what it is for.

Alignment: the program charter should be aligned and consistent with the
following documents: Portfolio roadmap, Business case, Program management plan,
Organizational change management plan.

Writing guidance:

*   State the purpose as the change the program exists to bring about, not as a
    description of the work. "Replace the billing platform" describes work; "so
    that month-end billing closes in three days rather than ten" describes a
    change, and only the second can be judged complete or not.

*   Give every objective a measure and a date. An objective that cannot be
    tested cannot be reported against, and an objective reported against only
    by opinion is indistinguishable from an aspiration.

*   Name the authority the program manager holds, and equally what they do not
    hold. A charter that grants everything appears to grant everything, and the
    first real escalation then has no precedent to follow.

*   Record the funding envelope as an assumption where it is not yet approved. A
    charter that treats unapproved funding as available sets the program up to
    discover the shortfall after it has committed the component projects.

*   Record what happens when an objective is not met. A charter with no stated
    response to failure leaves that decision to whoever happens to be in the
    room when it arises.

Tailoring Notes:

*   A program charter may be combined with a business case where the
    organisation treats them as one approval artefact. If they are combined,
    keep both sets of content: the business case answers whether the program is
    worth doing, the charter answers who is accountable for doing it.

*   The components section may be a portfolio extract rather than a maintained
    list, where components change faster than the charter is revised. The form
    should say which, so a reader does not treat an extract as authoritative.

*   Add or remove sections as the program's own governance requires. A program
    with a formal benefits mandate carries a benefits section that a program
    without one does not need.

*   Where the program is small enough that one person holds all the authority,
    say so explicitly rather than leaving the authority section blank, and
    record which authority is being retained elsewhere.

Column guidance, by column:

Objective rows:

*   **ID:** The identifier for the objective, used in the components, benefits
    and reporting sections so that progress against it can be traced.

*   **Objective:** What must be true when the program succeeds, stated so that
    someone who disagrees with it could say why.

*   **Measure:** How achievement will be established, naming the source of the
    figure rather than the sentiment. A measure with no source is a number
    nobody can reproduce.

*   **Target Date:** When the objective must be met, which is what makes it a
    target rather than a direction.

*   **Owner:** The single role accountable for the objective, which is normally
    not the program manager for every objective.

*   **Status:** Where the objective currently stands, from a fixed set.

Component rows:

*   **Component ID:** The stable identifier of the component project, matching
    the identifier used in the portfolio roadmap.

*   **Component Name:** The name of the project or operation within the program.

*   **Objective Linkage:** Which program objectives this component serves. A
    component linked to no objective is a candidate for removal, and the charter
    is where that becomes visible before the money is committed.

*   **Status:** Where the component currently stands, from the fixed set used
    across the program.

*   **Owner:** Who is accountable for the component, which will usually not be
    the program manager.

Benefit rows:

*   **Benefit ID:** The identifier for the benefit.

*   **Benefit:** The benefit the program expects to produce.

*   **Category:** Whether it is financial or non-financial. The two are
    governed differently, and a benefit recorded without a category is usually
    counted at the value the writer found most convenient.

*   **Beneficiary:** Who receives the benefit, named rather than described,
    because a benefit with no identifiable recipient is not a benefit the
    program can be held to.

*   **Realization Mechanism:** How the benefit will actually be captured, which
    is where most assumed benefits turn out not to be.

*   **Realization Date:** When the benefit is expected to be realised, which for
    a financial benefit is often well after the project that created it ends.

Authority rows:

*   **Decision Type:** What kind of decision this row concerns.

*   **Authority Level:** The level the program manager may decide at, such as
    team, department, or business unit.

*   **Escalation Path:** Who decides when the authority level is exceeded, named
    so the escalation does not have to be negotiated at the moment it is needed.

*   **Limits or Conditions:** What the authority does not extend to, which is
    the half of the row that prevents the dispute later.

Risk and assumption rows:

*   **ID:** The identifier for the risk or assumption.

*   **Type:** Whether the row is a Risk or an Assumption.

*   **Description:** What is at stake, or what is being taken for granted.

*   **Impact on Program:** What happens to the program if the risk occurs or the
    assumption proves false.

*   **Owner:** Who watches it.

*   **Review Date:** When it will next be checked.
-->
