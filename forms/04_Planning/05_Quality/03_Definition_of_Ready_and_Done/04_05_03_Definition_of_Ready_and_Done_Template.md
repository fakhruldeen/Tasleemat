Context and Definition:
A definition of ready and a definition of done are a standard rather than a
record. They are written once, at the start, and every piece of work is then
measured against them, which is what separates this from a checklist that is
filled in per item.

The two definitions point in opposite directions. The definition of ready is
a promise made by whoever brings work in, and it is the team's only legitimate
reason to refuse work. Its value depends on being small: a ready standard that
cannot be met is one that gets waived, and once it is waived the team has lost
the right to ask the question at all.

The definition of done is a promise made to whoever reads the work later, and
it is the one that decays. Every story shipped with an exception makes the
standard weaker for the next one, and nothing in the process stops that
exception becoming the rule. So the done criteria are written once and applied
without renegotiation, and a justified exception is logged as an exception
rather than folded back into the definition where nobody will see it.

Both are about evidence rather than intention. Ready does not mean the team
believes the work is well formed; it means somebody can check without asking
the author. Done does not mean the developer believes it works; it means a test
exists that somebody else ran.

It can receive information from:
*   The product backlog, which is where the acceptance criteria already live or
    should live
*   The team's retrospective findings, which is where a criterion that is being
    waived should be reported
*   The estimation record, so the ready standard reflects what estimating
    actually requires

It provides information to:
*   The sprint planning log, which applies the ready standard when work is pulled
*   The team performance assessment, which can only be read against a standard
*   The change log, because a change that was not tested is the change the done
    standard exists to prevent

Tailoring Tips:
*   Keep the ready standard short. It is the only reason the team can refuse
    work, and a standard that cannot be met is a standard that will be waived.
*   Write the done standard once and apply it without renegotiation. A
    justified exception belongs in an exception log, because a definition that
    is quietly rewritten is one nobody can hold anybody to.
*   Make every item checkable by somebody other than its author. Both
    definitions are about evidence, and the moment an item can only be confirmed
    by the person who wrote it, it is a statement of confidence rather than a
    criterion.

Alignment:
The definition of ready and done standard should be aligned and consistent with:
*   The team's estimation record, so the ready standard reflects real practice
*   The retrospective, which is where a criterion that keeps being waived is
    reported rather than quietly dropped
*   The change control process, since a change that has not been tested is the
    case the done standard exists to catch

Section Instructions:
*   Definition of Ready (DoR): the conditions work must satisfy before the team
    picks it up, each written so a second person can check it.
*   Definition of Done (DoD): the conditions that must hold before work is
    called finished, each written so somebody other than the author could
    confirm it.
